## 1 问题背景与探测动机

### 1.1 既有评测中的选项顺序设定

在此前完成的 CLERC 法律检索（Top-30 候选，[setwise_decision_rerank.ipynb](file:///home/lzx/projs/textual-view/experiments/setwise-decision-rerank/notebooks/setwise_decision_rerank.ipynb)）与 STaRK-Prime 生物医学检索（Top-20 候选，115 道命中题，[stark_prime_setwise_rerank.ipynb](file:///home/lzx/projs/textual-view/experiments/setwise-decision-rerank/notebooks/stark_prime_setwise_rerank.ipynb)）两轮重排序实验中，所有方法接收的候选列表 `cids` 均固定为 **BM25 初始检索得分从高到低的顺序（Rank 1 → Rank 20/30）**（见 [rerank_lib.py](file:///home/lzx/projs/textual-view/experiments/setwise-decision-rerank/rerank_lib.py#L614-L822) 与 [stark_rerank_lib.py](file:///home/lzx/projs/textual-view/experiments/setwise-decision-rerank/stark_rerank_lib.py)）：

1. **Pointwise (`Noul`)**：每个候选在独立请求或独立 question 分支中打分，理论上对候选输入顺序严格不敏感（仅在得分完全相同时以 `cids.index(c)` 打破平局）。
2. **One-shot Setwise (`Choice-20` / `Choice-30`)**：将 20 或 30 个候选放入同一个 `choice` 问题中一次性输出归一化概率分布。
3. **多阶段 / 结构化 Setwise（`Tournament`、`Sliding Window`、`Heap Sort`）**：不仅单次 `Choice` 调用内部存在选项排列顺序，初始分组本身也直接依赖 BM25 顺序（如 `Tournament 4x5->8` 将 BM25 Rank `1..5` 分入第 1 组、`6..10` 分入第 2 组）。

### 1.2 三类 Decision Model 对选项顺序敏感的潜在机理

- **`AnyJev (Tacit-9B)`**：将 `criteria` 中的选项按顺序映射为字母标签 `(A), (B), (C), ...` 并读取末尾 token 在 `A..Z` 词表上的 logits。若模型对靠前位置或特定字母标签存在先验偏好（Primacy / Label Bias），固定按 BM25 顺序输入会将位置偏置与 BM25 头部候选本身较高的相关性混杂。
- **`Kev-9B`**：基于 `Qwen3.5-9B-Base`（含 Gated DeltaNet 线性注意力层的混合架构），各 `<opt> ... </opt>` 片段在序列中按因果顺序编码（[kev/model.py](file:///home/lzx/projs/textual-view/references/repos/kev/kev/model.py#L69-L110)），后出现的选项在编码其 `</opt>` 向量时能看到前面的选项。其官方服务端 [kev/serve.py](file:///home/lzx/projs/textual-view/references/repos/kev/kev/serve.py#L255-L276) 专门提供了 `/v1/systemone/permute` 接口来评测 `Choice` 在多次随机顺序下的 `argmax_stable` 与概率极差 `spread`。
- **`Google Gemini Decision 1`**：黑盒 API（`POST https://generativelanguage.googleapis.com/v1beta/decisions`），在 STaRK-Prime 115 题的 `One-shot Setwise Choice-20 (criteria)` 上取得了 `68.7%` 的 Hit@1。我们需要通过受控实验弄清其内部对选项顺序与键名的真实处理方式。

  - **正确答案集合（共 3 个并列正确实体）**：

    - `3342`（`ABLIM2`）：BM25 初始排名 **#17**

- **五个递进问题**：

  2. **正序 / 倒序 / 随机打乱**：调换候选顺序后，概率是否变化？`criteria` 模式与 `tagged` 模式为何表现不同？

  5. **在 `instructions` 中声明“随机顺序排列”的作用**：既然 `criteria` 模式在服务端重排后本身具有未知/伪随机顺序，在 `instructions` 中显式声明“候选按随机顺序排列”，对比 3 次随机打乱后的概率分布，声明随机与不声明随机哪个更能帮助正确答案胜出？

## 2 核心概念与报文结构拆解：`criteria` 模式、`tagged` 模式与键名排序机制

在调用 `Gemini Decision 1` 的 `choice` 接口时，请求体主要包含两个字段：
- **`input`**：公共背景文本字符串（所有选项共享的上下文）。
- **`questions.<qid>.criteria`**：一个 **JSON 对象/字典 `{ "键名(Key)": "选项描述(Value)" }`**，模型最终对每个 Key 输出归一化概率（所有 Key 的概率之和为 `1.0`）。

以 3 个候选文档 `432`、`3188`、`4815` 为例，下面直观对比两种模式与不同键名策略的 JSON 报文差异。

### 2.1 `criteria` 模式 vs `tagged` 模式的区别

这两种模式的核心区别在于：**候选文档的长正文究竟是放在 `criteria` 选项字典的 Value 里，还是拼在 `input` 公共背景字符串里。**

#### （1）`criteria` 模式（正文直接作为 `criteria` 字典的 Value）

```json
{
  "input": "Query Excerpt:\nWhich gene or protein is engaged in...",
  "questions": {
    "best_passage": {
      "type": "choice",
      "instructions": "Which candidate biomedical entity from the STaRK-Prime knowledge base best satisfies...",
      "criteria": {
        "432":  "- name: PDLIM7 ...",
        "3188": "- name: ABLIM3 ...",
        "4815": "- name: ABLIM1 ..."
      }
    }
  }
}
```
- **顺序由谁决定**：完全取决于 Google 服务端以什么顺序遍历并序列化 `criteria` 这个 JSON 对象中的键值对。

#### （2）`tagged` 模式（正文贴上 `[ID]` 标签拼入 `input` 字符串，`criteria` 仅保留短标签指代）

```json
{
  "input": "Query Excerpt:\nWhich gene or protein...\n\nCandidate Passages:\n[432] - name: PDLIM7 ...\n\n[3188] - name: ABLIM3 ...\n\n[4815] - name: ABLIM1 ...",
  "questions": {
    "best_passage": {
      "type": "choice",
      "instructions": "Which candidate biomedical entity from the STaRK-Prime knowledge base best satisfies...",
      "criteria": {
        "432":  "Passage [432]",
        "3188": "Passage [3188]",
        "4815": "Passage [4815]"
      }
    }
  }
}
```
- **顺序由谁决定**：因为 `input` 是一个**普通的纯文本字符串**，服务端不会修改 `input` 字符串内部的段落顺序。当客户端在 `tagged` 模式下将候选列表倒序或随机打乱时，`input` 字符串中 20 篇文档的物理先后位置会实打实地发生改变。

### 2.2 为什么 `criteria` 模式下直接颠倒 Python `dict` 顺序不会改变结果？

在 JSON 规范与 Google 服务端的 Protobuf 解析器（`map<string, Value>`）中，JSON 对象 `{...}` 是无序映射。Google 服务端接收到 `criteria` 后，**会忽略客户端 JSON 文本中键值对的书写顺序，先按 Key 字符串的字典序（Lexicographical Order）对所有选项做规范化排序**，然后再拼接成底层模型的输入序列。

因此：
1. **当使用原节点 ID（`"432"`, `"3188"`, `"4815"`, `"10858"`, ...）作为 Key 时**：
   不管客户端在发送前把 Python `dict` 按 BM25 正序、倒序还是随机顺序构造，到了服务端按 Key 的字符串字典序（`"10858"` < `"1233"` < `"128284"` < ... < `"3188"` < `"3342"` < `"432"` < `"4815"` ...）重排之后，**喂给底层模型的永远是完全相同的顺序**。
2. **当改用代表位置序号的 `"opt_00" .. "opt_19"` 作为 Key 时**：
   由于 `"opt_00"` < `"opt_01"` < ... < `"opt_19"` 的字典序恰好等于位置序号 `00 → 19`，客户端把不同文档绑定到 `opt_00 .. opt_19` 时，就能强制控制服务端按字典序排列后各篇文档进入模型的真实物理顺序。

> **对既有 STaRK-Prime 实验结论的重要推论**：
> 此前我们在 STaRK-Prime 上用 `criteria` 模式评测 `Gemini Decision 1` 时，使用的是候选节点的真实 `node_id` 作为 Key。由于服务端按 `node_id` 的字符串字典序重排了选项，**模型在实际评测中看到的选项顺序与 BM25 的初始检索排名完全无关**（相当于自带了一次按 ID 字典序的伪随机打乱）。因此，此前 `One-shot Setwise Choice-20 (criteria)` 取得的 `68.7%` Hit@1 **完全没有依赖“BM25 第一名排在最前面”的位置先验红利**。

> **工程缓存注意事项**：
> 本地缓存类 `DiskCache.make_key`（[rerank_lib.py](file:///home/lzx/projs/textual-view/experiments/setwise-decision-rerank/rerank_lib.py#L103-L105)）在计算 SHA-256 时使用了 `json.dumps(..., sort_keys=True)`。若开启本地缓存，仅改变 Python `dict` 插入顺序的两次 `criteria` 请求在本地就会命中同一个缓存键。为确保严谨，本文记录的所有探测实验均设置 `cache=None`，每次请求均直接发往 Google 远端 API。

## 4 实验二：剥离“纯键名字符串效应”与“纯位置移动效应”

### 4.1 严格相同顺序下，单纯更换中性键名（原节点 ID vs `opt_00..opt_19`）

先把 20 个候选按原节点 ID 的字符串字典序排好（`sorted_cids = sorted(cids)`），让 `opt_00 .. opt_19` 对应的文档顺序与原节点 ID 字典序 **100% 相同**。此时两次请求在服务端按 Key 字典序排完后，**20 篇文档进入模型的先后位置完全一致，唯一改变的只有键名字符串本身**（例如第 16 个位置的键名从 `"4815"` 变成 `"opt_15"`）。

此外，经核查 SQLite 文档库，STaRK-Prime 候选文档的正文内容（如 `- name: ABLIM1 ...`）**并不包含 `4815`、`3342`、`3188`、`432` 这些数字节点 ID 字符串**。

| 候选 ID (`*`为正确答案) | 在字典序中的固定位置 | 原 ID 作键名 (`"4815"` 等) | `opt_XX` 作键名 (完全同顺序) | 差值 (`ID - opt_XX`) |
|---|---:|---:|---:|---:|
| **`4815 *` (ABLIM1)** | 第 16 个 | `0.715843` (#1) | `0.749425` (#1) | `-0.033581` |
| **`3342 *` (ABLIM2)** | 第 12 个 | `0.105840` (#2) | `0.111416` (#2) | `-0.005576` |
| **`3188 *` (ABLIM3)** | 第 11 个 | `0.078947` (#3) | `0.073509` (#3) | `+0.005439` |
| `1233` | 第 2 个 | `0.070574` (#4) | `0.028520` (#4) | **`+0.042055`** |
| `10858` | 第 1 个 | `0.010190` (#5) | `0.012105` (#5) | `-0.001915` |

- **原因解释**：与本地 `Kev-9B` 的 `kev/api.py`（将 `criteria: {key: desc}` 格式化为 `<opt> {key}: {desc} </opt>`）一致，`Gemini Decision 1` 也会把 **键名（Key）本身作为选项标题/前缀拼入选项的 token 序列中**。因此，即使顺序完全相同，把键名从 `"4815"` 换成 `"opt_15"` 也会改变每个选项开头的几个 token，带来最大约 `0.042` 的轻微扰动（不改变 Top-5 排序）。

### 4.2 保持正确答案键名一个字符都不改，仅移动其在字典序中的前后位置

为了彻底隔离键名变化、只观察位置移动：
- **保持 3 个正确答案的键名始终为 `"4815"`、`"3342"`、`"3188"`（完全不变）**；
- 仅通过给另外 17 个错误干扰项的键名加上前缀 `"z_"` 或 `"0_"`，使这 3 个正确答案在字典序中被推到**最前面（第 1~3 位）** vs **最后面（第 18~20 位）**：

2. **对正确答案具有强烈的放大与分流效应**：把最佳正确答案 `4815` 的键名改为 `opt_15_best_correct_answer` 或 `"best"`，其概率从 `0.72 ~ 0.75` 直接拉升至 **`0.967 ~ 0.985`**；反之若改为负面标签 `opt_15_wrong_irrelevant`，其概率下跌 `-0.111`（从 `0.749` 降至 `0.639`），被压低的部分自动分流给了另外两个正确答案 `3342`（`0.111 → 0.158`）和 `3188`（`0.074 → 0.149`）。
3. **正文内容依然是第一决定因素**：即便给完全无关的垫底错误文档贴上 `"best_correct_answer"`，它也无法越过真正匹配查询约束的 3 个正确答案夺走第 1 名。这提示在实际评测与系统设计中，`criteria` 的键名应始终采用**无语义偏向的中性标识符**。

## 6 实验四：在 `instructions` 中声明“随机顺序排列”对 3 次随机打乱的影响与胜出能力分析

### 6.1 实验设计

既然 `criteria` 模式在服务端按 Key 重排后本身具有未知/伪随机顺序（而在 `tagged` 模式下也可能遇到候选顺序随机或初排质量不佳的情况），我们在 `instructions` 中显式追加一句“随机顺序声明”：

- **默认 `instructions`**：
  > `"Which candidate biomedical entity from the STaRK-Prime knowledge base best satisfies all requirements, attributes, and conditions specified in the query?"`
- **追加随机顺序声明后的 `instructions`**：
  > `"Which candidate biomedical entity from the STaRK-Prime knowledge base best satisfies all requirements, attributes, and conditions specified in the query? Note: The candidate entities are presented in a completely random order; their position or option label carries no information about relevance. Evaluate each candidate strictly based on its text content."`

使用 3 个固定随机种子（`seed = 101, 202, 303`）生成 3 组随机打乱顺序（`shuf1`, `shuf2`, `shuf3`），分别在 **`tagged` 模式** 与 **`criteria (opt_00..19)` 模式** 下对比声明前后的概率分布与极差（`spread = max - min`）。

### 6.4 深入分析：同样使用 `criteria` 模式，声明随机 vs 不声明随机，哪个更能帮助正确答案胜出？

由于 `QID = 9` 有 **3 个并列的正确答案（`4815`, `3342`, `3188`，同属 ABLIM 蛋白家族）**，而 `Choice` 的 20 个选项概率总和恒为 `1.0`，衡量“正确答案对错误干扰项的胜出能力”不能只看单个正确答案与其他两个正确答案之间的内部分配，而应考察正误阵营之间的四个核心对抗指标：

1. **3 个正确答案拿到的总概率 `Σ P(Gold) = P(4815) + P(3342) + P(3188)`**（越高越好）；
2. **17 个错误干扰项分走的总泄漏概率 `Σ P(Wrong) = 1 - Σ P(Gold)`**（越低越好）；
3. **最强错误干扰项得分 `max P(Wrong)`**（即第 4 名错误答案的概率，越低越不容易篡位）；
4. **最弱正确答案（#3）对最强错误答案（#4）的安全领先边际 `Margin = min P(Gold) - max P(Wrong)`**（越大代表正误边界越稳固）。

#### 表 10：`criteria` 模式下“不声明随机” vs “声明随机”的正误对抗指标对比

| 正误胜出核心指标（`criteria` 模式，`shuf1 / shuf2 / shuf3`） | 不声明随机顺序（默认 instructions） | **声明随机顺序（+ Random-Order 声明）** | 对比结论 |
|---|---|---|---|

| **正误分界安全边际 `Margin (#3 Gold - #4 Wrong)`** | `+11.85%` / **`+5.71%`** / `+13.64%`<br>（最不利顺序下仅领先 `+5.71%`） | `+8.76%` / **`+9.38%`** / `+17.44%`<br>（最不利顺序下仍领先 **`+8.76%`**） | **声明随机明显更优**：最坏打乱顺序下的安全边际**扩大了 +53%**（`5.71% → 8.76%`） |

**机理总结**：
- 当 `criteria` 送入服务端后，由于服务端按 Key 字典序（或未知内部规则）排列选项，模型看到的选项顺序本质上就是随机的。
- 若**不声明随机顺序**，模型会隐式赋予靠前位置/编号微弱的先验权重，导致排在前排的错误干扰项（如 `shuf1`/`shuf2` 中的 `3979`）白白分走 `2.55% ~ 3.58%` 的概率。
- 当在 `instructions` 中**显式声明“候选按随机顺序排列，位置和标签不含相关性信息，请严格根据正文内容评估”**后：
  1. 模型对错误干扰项的压制更加一致，头号错误干扰项的概率在每次打乱中都被压低到 `1.29% ~ 1.42%`（降幅近半），干扰项极差下降了 77%（`0.0331 → 0.0075`）；
  2. 3 个正确答案拿到的总概率被极其稳定地锁定在 **`95.60% ~ 96.72%`**（极差仅 `1.12%`），其余波动仅发生在 `ABLIM1/2/3` 三个同为正确答案的并列实体内部；
  3. 无论在 `criteria` 模式还是 `tagged` 模式下，显式声明随机顺序都能显著扩大正确答案相对于错误干扰项的胜出安全边际。

## 7 总结与后续实验启示

1. **单次前向确定性**：`Gemini Decision 1` 在相同请求报文下的多次调用具有 **100% 确定性**（双精度浮点差值为 `0`）。
2. **`criteria` 模式的字典序规范化与隐式去偏**：Google 服务端在解析 `criteria` JSON 字典时会按 **Key 字符串的字典序**重排选项。这一机制使此前使用原始 `node_id` 作为 Key 的 `Choice-20 (criteria)` 实验天然打乱了 BM25 初始排序，证实其高准确率（STaRK-Prime 115 题 `68.7%` Hit@1）并非来自 BM25 首位偏置。
3. **键名（Key）参与选项文本编码**：服务端会将 `criteria` 的 Key 作为选项前缀拼入模型输入。中性换名（如 `4815` → `opt_15`）在同顺序下仅引起 `≤ 0.042` 的轻微扰动；但带有强烈语义倾向的键名（如 `opt_XX_best_correct_answer` 或 `"best"`）会产生显著的提示词注入效应（可使垫底错误答案概率暴涨 317 倍冲至第 4 名，或使正确答案概率升至 `0.985`）。因此在重排序评测与应用中必须使用无语义倾向的中性键名。
4. **`criteria + 随机顺序声明` 的协同价值**：由于 `criteria` 模式天然带来了按 Key 字典序的伪随机排列，在 `instructions` 中配合声明“候选按随机顺序排列、位置与标签无关相关性”，能够有效消除模型对前排错误干扰项的位置先验，把头号错误干扰项的概率砍半（`2.60% → 1.34%`），并在 `tagged` 模式下将随机顺序极差砍半（`0.248 → 0.116`）、挽救因排位不利而掉队的正确答案。
